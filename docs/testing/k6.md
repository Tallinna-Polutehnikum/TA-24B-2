# k6 screening API load test

## System Requerements for the test
- AMD Ryzen 5 3600 6-Core Proccessor or Intel Core i5-6500K 4-Core Proccessor
- Fast SSD (for speed, M.2 will be perfect for the test)
- Windows 10 or newer
- Docker with pre-installed MySQL structure
- Node.js with pre-installed npm
- Git Bash or PowerShell 

## What k6 measures

k6 generates concurrent HTTP requests and reports request rate, latency, and failed requests. This scenario loads the screening list for one movie through the local NestJS API.

## Local setup (for k6 beginners and advanced testers)

Run this test only against your local Docker database and local API. Do not try or point on cloud or open enviroment, it can cause the further problems with your database and public product.

`From the repository root, start MySQL:`

```powershell or git bash
docker compose up -d --wait
```

`For a fresh, empty local database, initialize it and generate a larger dataset:`

```powershell or git bash
cd backend
npm ci
if (!(Test-Path .env)) { Copy-Item .env.example .env }
npm run db:migrate
npm run db:seed
$env:MOVIE_COUNT = "100"
npm run movies:generate
```

ATTENTION! For an existing database, follow the database setup instructions in the repository README. Do not run `db:fresh`, because it deletes data.

`Check the number of screenings:`

```powershell
docker exec apollo-kino-mysql mysql -uapollo -papollo apollo_kino -e "SELECT COUNT(*) AS screenings FROM screening;"
```

`Start the API from the `backend` folder:`

```powershell
npm run dev
```

`In another terminal, find a movie ID and confirm that its screenings endpoint responds:`

```powershell
$movies = Invoke-RestMethod http://localhost:3000/movies
$movies | Select-Object -First 5 id, title
$env:MOVIE_ID = "15"
Invoke-RestMethod "http://localhost:3000/movies/$env:MOVIE_ID/screenings"
```

Replace `15` with an ID from the returned movie list.

## Scenario and run command

The script in `tests/load/k6-screenings.js` requests `GET /movies/{MOVIE_ID}/screenings`. It checks for HTTP 200 and uses thresholds of less than 1% failed requests and a p95 latency below 500 ms. The virtual-user count and duration can be overridden with environment variables.

`Run a short smoke test:`

```powershell
Get-Content .\tests\load\k6-screenings.js -Raw |
  docker run --rm -i -e BASE_URL=http://host.docker.internal:3000 -e MOVIE_ID=$env:MOVIE_ID -e VUS=1 -e DURATION=5s grafana/k6 run -
```

`Run the measured scenario:`

```powershell
Get-Content .\tests\load\k6-screenings.js -Raw |
  docker run --rm -i -e BASE_URL=http://host.docker.internal:3000 -e MOVIE_ID=$env:MOVIE_ID -e VUS=20 -e DURATION=30s grafana/k6 run -
```

Docker downloads the k6 image automatically on the first run. The API is accessed from the k6 container through `host.docker.internal`.

## Results

## Measured on 2026-11-26 against the local development API and local MySQL database:

| Metric | Result |
| --- | ---: |
| Rows in `screening` | 8,394 |
| Movies in database | 172 |
| Screenings returned for tested movie | 540 |
| Virtual users | 20 |
| Test duration | 30 s |
| Requests | 728 |
| Request rate | 23.69 requests/s |
| Mean latency | 833.72 ms |
| p95 latency | 1.14 s |
| Failed requests | 0% |
| HTTP checks passed | 728/728 |

## Composite index experiment

The original query plan used `screening_movie_id_index` and reported `Using where; Using filesort`. I added a temporary local index on `(movie_id, starts_at)`; the plan then used that index and no longer reported a filesort.

| Setup | Requests | Request rate | Mean latency | p95 latency | Failed requests |
| --- | ---: | ---: | ---: | ---: | ---: |
| Existing `movie_id` index | 728 | 23.69/s | 833.72 ms | 1.14 s | 0% |
| Temporary `(movie_id, starts_at)` index | 714 | 23.21/s | 850.52 ms | 1.32 s | 0% |

The temporary index did not improve end-to-end latency in this run and was removed from the local database. Each configuration was measured once, so the difference may include run-to-run variation.

## Conclusion

The endpoint returned successful responses, but under 20 concurrent virtual users its p95 latency was 1.14 seconds, above the selected 500 ms threshold. The temporary composite index removed the filesort in the query plan, but did not improve the HTTP measurement. Since the endpoint returned 540 screenings per request, limiting or paginating the response may be more promising to test than adding this index. The test ran against the development API, so repeat measurements in production mode would help isolate application overhead.

Results may vary by system or PC. The measurements are not a production-capacity guarantee that everything can be stable in other machines.

A local attempt to run `npm run movies:generate` with `MOVIE_COUNT=150` took more than 14 minutes and was stopped before completion. The generator creates Faker data locally and stores Picsum URLs in the database; it does not download those images during generation. The cause of the long runtime was not isolated, so attributing it to RAM or internet latency would be speculative. Mostly it happens because of Lorem Picsum API-website big latency and crash.
